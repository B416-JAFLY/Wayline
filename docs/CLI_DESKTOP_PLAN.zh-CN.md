# CLI 与 desktop 统一及固件烧录实施方案

目标是让 desktop 面向普通用户，CLI 面向脚本和诊断，两端共用发现、收发、配置和设备管理能力。普通用户最终只需安装成品软件、连接 Cardputer Adv，再通过界面完成固件安装与文件传输。

七个阶段的代码已接入同一调用链。各阶段勾选项表示实现状态；文末另列实机与发布验收状态。完整包安装与覆盖更新、CLI 和 desktop 对 Cardputer Adv 的同布局升级、桌面设置退出、板端串口回归和已安装服务权限测试已通过。异常恢复、Apple 设备互通、标准普通账号桌面流程以及无开发工具的干净 Windows 验收仍待完成。当前操作说明见 [README](../README.zh-CN.md)、[快速开始](QUICKSTART.zh-CN.md) 和[开发指南](DEVELOPMENT.md)。

## 范围和约束

- 保留 `omdrop-desktop.exe` 的普通用户界面进程与 `--service` 高权限进程。界面不提升权限，以保持资源管理器拖放可用。
- 保留 CLI 作为可选工具。桌面提供托盘、拖放和交互提示；CLI 提供稳定参数、退出码和机器可读输出。
- 保留独立服务入口，兼顾无桌面部署。OWL 仍由服务管理，不要求用户手动运行 `owl.exe`。
- 首版固件烧录只支持 ESP32-S3 / Cardputer Adv、原生 USB Serial/JTAG 和当前 8 MiB Flash 配置。
- 固件仍独立构建；用户端安装和烧录不依赖 Rust、Python、ESP-IDF、CMake 或 Git。
- 首轮不加入 OTA、浏览器烧录、其他开发板适配或传输性能优化。固件 UI、无线协议和依赖升级仅在阶段目标确实需要时修改。

| 模块 | 目标职责 |
| --- | --- |
| `apps/desktop` | 界面、托盘、资源管理器集成、接收确认、固件操作展示与用户流程 |
| `apps/cli` | 参数解析、终端交互、JSON 输出、退出码；调用共享业务能力 |
| `crates/omdrop-core` | AirDrop 协议、发现、流式收发、取消、结果和错误语义 |
| `crates/omdrop-service` | 公共服务客户端、SCM 访问、会话协调、OWL 管理、维护模式和防火墙 |
| `crates/omdrop-host` | 两端共用的用户配置、身份加载、接收广播标识及改名记录、默认目录和 AWDL 网卡选择；不依赖 GPUI |
| `crates/omdrop-flash` | 固件包校验、维护协调、烧录工具调用、进度、取消与启动检查；不依赖 GPUI |
| `firmware` | 板端程序；继续使用独立 Cargo/ESP-IDF 工程 |
| `scripts` 与发布资源 | 开发者构建、固件打包、成品打包及预编译文件安装 |

两端通过 `omdrop-host` 获取宿主配置和核心身份，通过服务客户端取得使用会话。`omdrop-flash` 内部协调维护许可和设备互斥。高权限服务不依赖界面模块，不接受客户端传入任意命令来执行。

CLI 不链接 GPUI。UI 状态、参数解析和终端提示保留在应用入口，共享业务规则放在对应 crate。

## 阶段 1 共用服务客户端

共享客户端集中命名管道请求、超时和错误分类；收发授权与服务生命周期分别由后续模块处理。

- [x] 在 `omdrop-service` 新增 `client` 模块，复用 `protocol::Request` 和 `Status`，提供读取状态、请求防火墙配置等接口。
- [x] 将管道名称和请求超时作为客户端配置，测试可使用独立管道；保留当前有界读取、换行校验和管道忙时的等待。
- [x] 明确区分连接失败、超时、响应格式错误和服务返回的业务错误。状态查询允许呈现故障快照，控制请求不能把失败响应当成成功。
- [x] desktop 和 CLI 接入公共客户端，删除已被替代的重复实现。界面中文提示仍由 desktop 负责，CLI 保留适合终端的上下文。
- [x] 保留当前 JSON 字段和已有解析兼容性；阶段内不更改 `start`、`stop`、`set` 的含义。

主要文件：`crates/omdrop-service/src/client.rs`、`lib.rs`、`protocol.rs`、两端 Cargo 清单、desktop `backend.rs` 和 CLI `main.rs`。

验收：模拟管道覆盖正常响应、服务报错、超长响应、缺失换行、非法 JSON、超时、忙管道和服务未安装；两个入口得到一致的错误类别。服务、CLI 和 desktop 测试通过，常规构建不访问无线串口。

## 阶段 2 统一授权和传输结果

将“用户是否同意接收”与传输协议处理分开，同时让 CLI 的取消行为使用已有的核心取消机制。

- [x] 接收默认不自动授权。desktop 保持确认卡片；CLI 在交互式终端显示发送方、文件清单和保存位置后询问。
- [x] CLI 新增显式 `--accept-all`，仅对本次接收命令有效。非交互环境没有明确接收策略时，在启动接收前报错；不悄悄自动接受，也不等待无法输入的提示。
- [x] 输入结束、等待超时、取消或提示界面失效均拒绝请求。并发请求采用有界队列，避免多个工作线程同时读取终端输入。
- [x] CLI 的 Ctrl+C 接入共享取消对象，清理发现、传输、接收连接和 mDNS 广播；桌面取消按钮使用相同的终止语义。
- [x] 两端统一区分成功、对方拒收、本地取消、连接中断和数据校验失败。上传达到 100% 后仍等待最终协议确认。
- [x] 调整 `ReceiverOptions` 默认值时逐一核对构造位置和测试夹具，让自动接收场景显式选择该策略。

主要位置：`omdrop-core` 的 `receiver.rs`、`sender.rs`、`cancel.rs`，CLI `main.rs`，desktop `backend.rs` 与 `receiving.rs`。

验收：覆盖接受、拒绝、EOF、超时、非终端运行、明确自动接收、取消与最终确认竞争、上传结束后失败和部分文件清理。两端只在相同的协议条件下报告成功。

## 阶段 3 协调多个客户端与服务退出

引入“使用会话”：desktop 或 CLI 正在使用无线能力时，向服务登记并持有会话；操作结束时释放。服务统一判断无线设备是否仍被使用。

- [x] 在 `omdrop-service` 中集中 SCM 访问，区分 Windows 服务生命周期与无线配置。现有管道 `stop` 会持久化禁用无线，不能拿它代替退出会话或临时暂停烧录。
- [x] 建立专用的长连接会话管道，沿用本地访问限制，并由服务核对连接方进程身份。会话令牌绑定服务实例，不能跨服务重启复用；连接断开或进程退出可触发回收。
- [x] 会话协议提供版本和能力协商。旧服务缺少会话能力时提示更新，避免以不完整的协调机制启动并发操作。
- [x] 首版每台无线设备最多一个发送任务和一个接收监听，允许发送与接收并行。第二个发送任务或接收监听返回明确的占用状态；desktop 正在接收时 CLI 不另起同一端口的监听。
- [x] desktop 托盘退出只取消并释放自己的任务。CLI 仍在使用时服务继续运行；最后一个会话退出时，按需服务停止并回收 OWL，再完成服务退出。
- [x] 独立自动启动服务保留常驻模式。按需模式与常驻模式由服务启动配置明确区分，退出客户端不改写用户保存的无线配置。
- [x] 处理首次启动等待会话、最后会话释放、新客户端同时加入和服务崩溃重启。服务开始退出后拒绝新会话并让客户端等待重启，不能把半退出状态当成可用。

分为三个可独立验证的开发步骤：会话协议与状态机、两端接入、并发与异常退出测试。协调逻辑由服务串行处理，不依赖两个客户端各自统计进程数量。

验收：双客户端任意退出顺序、客户端崩溃、启动与退出竞争、服务重启、接收占用和常驻模式均有测试。单独运行 desktop 时仍满足“托盘退出后后台与 OWL 退出”；有其他使用者时 UI 正确解释后台继续运行的原因。

## 阶段 4 共用配置并简化 CLI

`omdrop-host` 集中两端相同的宿主操作。UI 状态、托盘、缩略图和参数解析继续留在各自应用。

- [x] 共享设备名校验、用户身份目录、默认保存目录和 AWDL 网卡选择。沿用现有配置路径和已保存值，扩展字段时保留未修改设置。
- [x] 身份首次创建使用跨进程互斥，避免 CLI 与 desktop 同时启动时各自生成并覆盖证书。
- [x] CLI 参数优先于用户配置，用户配置优先于默认值。临时参数只影响本次运行；仅明确的保存操作写入配置，写入保持原子性并处理并发更新。
- [x] 在 Windows 下自动发现 `awdl0` 和有效链路本地地址。手动指定网卡参数仍可用于诊断，但必须成对校验，不拼接来自不同接口的地址与索引。
- [x] CLI 发送、发现和无线接收按需取得会话；状态查询不自动启动服务。保留显式 TCP 绑定的本地诊断能力。
- [x] 新增 `status`、`doctor` 和 `--json`。`doctor` 默认只诊断，不安装服务、修改防火墙或抢占串口。
- [x] JSON 模式使用带 `schemaVersion` 和事件类型的 JSON Lines，stdout 只输出结构化数据，诊断信息进入 stderr；交互提示不混入 JSON 输出。

JSON 模式和非交互式发送要求显式选择目标；发现重名设备时返回歧义错误，不自行选择第一个接收方。

命令示例：

```powershell
omdrop-cli status --json
omdrop-cli discover
omdrop-cli send --to "iPhone" -- "C:\Users\Example\Pictures\photo.jpg"
omdrop-cli receive
omdrop-cli receive --accept-all --save "C:\Users\Example\Downloads\Omdrop"
omdrop-cli doctor
```

| 退出码 | 含义 |
| --- | --- |
| 0 | 命令成功；发现成功但结果为空也属于正常完成 |
| 2 | 参数或运行策略不完整，例如非交互接收未明确授权 |
| 3 | 服务、设备或指定接收方不可用 |
| 4 | 对方拒绝接收 |
| 5 | 操作失败，例如传输、文件写入或校验失败 |
| 6 | 资源被占用 |
| 130 | 用户取消 |

验收：同一配置下两端使用相同设备名、身份和网卡选择结果；中文及带空格路径可用；多个接口、无设备和损坏配置能正确报错。自动化测试核对 JSON 字段、终止事件与退出码，CLI 构建不依赖 GPUI。

## 阶段 5 提供共用的固件烧录能力

固件包和烧录流程位于公共 crate，桌面与 CLI 调用同一实现。Rust 调用随包分发的 Windows x64 独立 `esptool 5.0.2`，用户端不调用 ESP-IDF，也不临时安装工具。固定下载地址和 SHA-256 位于 [fetch-flash-tool.ps1](../scripts/fetch-flash-tool.ps1)，许可证及源码包随工具分发。

- [x] 新增开发者固件打包脚本，从同一次已成功构建的 `flasher_args.json` 收集 bootloader、分区表和应用，不混用不同构建的产物。
- [x] 固件包清单记录格式版本、板型、芯片、Flash 容量、源码版本、镜像相对路径、烧录偏移、长度、SHA-256 和工具版本。打包脚本验证镜像存在且布局一致。
- [x] 新增 `omdrop-flash`，先完成清单校验、设备枚举、兼容性检查和子进程管理，再实现烧录与校验。检查路径越界、地址重叠、容量越界和损坏镜像。
- [x] 新增服务维护会话。发起方先停止自己的空闲接收监听；存在正在进行的传输或其他客户端仍占用接收能力时返回占用提示，不强制打断。
- [x] 取得维护许可后阻止新任务，暂停 OWL 自动拉起，等待 OWL 退出并释放串口，再启动烧录。临时维护不修改 `enabled`。
- [x] 烧录工具使用明确的可执行文件路径和参数数组，不经过 shell 拼接。限制日志缓冲，跟踪子进程退出和清理；客户端崩溃时通过 Job Object 等机制回收其烧录子进程。
- [x] 烧录及重启检查结束后再释放维护许可，按原运行模式和现存会话恢复无线。维护连接丢失不能直接触发 OWL 与尚未退出的烧录进程抢占串口。
- [x] CLI 新增固件信息和烧录入口，复用公共事件、错误及退出码。未安装服务时也能刷写首次连接的设备；与服务重连、启动之间仍需设备级互斥。

设备级互斥必须同时接入服务启动和烧录启动，不能仅通过界面按钮状态实现。写入中失败且设备未就绪时，保留明确的维护失败状态并提供重试或恢复操作，避免 OWL 自动重启后反复抢占下载端口。

当前恢复策略按 COM 端口保留失败记录。设备重新枚举到新 COM 后，成功重刷只清除新端口记录，不清除旧端口记录；存在旧记录时自动选择模式继续停止 OWL。可显式配置已经通过启动检查的新端口，或核实旧设备后处理其记录。系统不会自动推断两个端口属于同一设备，拔线和跨端口恢复仍需实机验收。

固件操作状态采用 `校验固件包 → 取得维护许可 → 连接设备 → 写入 → 校验写入 → 检查启动 → 恢复无线`。失败结果应包含失败阶段、是否可能已经写入以及能否重试。

必须明确的产品规则：

- ESP32-S3 芯片型号不能证明开发板就是 Cardputer Adv。无法读取可靠板型时，由用户明确选择受支持板型；不能仅凭 USB 名称自动刷写。
- 首版按清单写入必要镜像，默认不整片擦除。已识别本项目固件且布局兼容的升级保留 NVS 等持久化分区；布局不兼容时阻止静默升级。
- 首次安装或替换其他固件时明确说明会替换现有程序与分区布局，不保证保留其他固件的数据。需要重新安装的升级必须走同样明确的用户选择，不能伪装成保留设置的更新。
- 固件包版本、协议版本与 ESP-IDF 版本分别标注。设备未提供应用版本时显示未知，不能用 IDF 版本冒充固件版本。
- 写入校验通过后才报告镜像已写入；握手通过后才报告设备已就绪。重启失败应保留“写入完成但设备未就绪”的区别。
- 写入开始后的取消或断电可能需要完整重刷，不承诺自动回滚。停止后先确认烧录进程退出，再允许其他串口使用者进入。

验收：模拟工具覆盖损坏包、错误芯片、多个串口、进程启动失败、无进度、异常退出、取消和服务恢复。Cardputer Adv 的 CLI 同布局升级已通过三镜像设备摘要校验和 HELLO 启动检查，升级前后分区表、NVS 与 PHY 区域逐字节相同。desktop 同布局升级也已通过，写入期间 OWL 退出，设备就绪后恢复无线。仍需验证独立烧录工具在无 Python 的干净 Windows 环境启动、首次替换其他固件，以及拔线和写入中取消后的恢复。

## 每阶段的验证与交付要求

先运行受影响模块的检查，跨模块共享接口变化再扩大到整个 Windows workspace。服务和 IPC 测试使用临时配置、独立管道和模拟子进程，不默认操作已安装服务。

```powershell
cargo test -p omdrop-service --all-targets --locked
cargo test -p omdrop-cli -p omdrop-desktop --all-targets --locked
cargo fmt --all -- --check
cargo clippy --workspace --all-targets --locked -- -D warnings
```

涉及整个共享调用链时补充 `cargo test --workspace --locked` 和 `scripts/build-desktop.ps1`。新增 crate 后，将其测试纳入对应阶段与 workspace 检查；涉及 OWL 时执行 `scripts/build-owl.ps1 -Test`。

固件或主机与固件共享协议变化时，按 [开发指南](DEVELOPMENT.md) 执行 `no_std` 检查、固件主机测试和实际 ESP-IDF 构建。模拟测试不能替代 Cardputer Adv 烧录及 Apple 设备互通验证。

每阶段交付内容为：实现代码、对应测试、已实现行为的文档、实际验证结果以及尚待实机验证的项目。仅在验收条件满足后标记完成；通过主机测试但未完成必需实机验证时，明确保留该阶段的验证项。
